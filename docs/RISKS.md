# Прогноз ошибок и как они закрыты

Что может пойти не так у жюри или на закрытой проверке, и что в проекте этому противостоит.
Каждая строка с пометкой «проверка» покрыта автотестом или `make verify`.

## Найдено и исправлено в версии 1.1

| Проблема | Чем грозила | Исправление | Проверка |
|---|---|---|---|
| Открытый генератор + seed → агент перебором восстанавливает эпизод и читает эталон (замерено: 13 с на 2000 seed) | утечка закрытых данных = блокировка оценивания | секрет оценщика `AUDITFORGE_SECRET` подмешивается в каждый эпизод, живёт только в процессе оценщика | `evaluator_secret_defeats_seed_regeneration`, `fuzz.regeneration_attack` |
| Доказательства с выдуманными ID засчитывались, если рядом был верный набор | «неподтверждённые доказательства» проходили | каждый ID доказательства обязан существовать в эпизоде | `invented_evidence_ids_are_never_accepted`, мутант `evidence_existence_not_checked` |
| Трюк «любая строка UNAPPLIED = ошибка распределения» давал точность 1,00 без анализа | среда поощряла простой трюк | законные авансы (платёж без счёта, честно в UNAPPLIED); трюк теперь даёт точность 0,33 | `test_advances_are_legitimate_unapplied_cash` |
| При 2 контрагентах генератор падал (10% случайных конфигураций) | неработающее ядро на «новых сочетаниях параметров» | гарантированный набор контрагентов + валидация конфигурации | `test_random_configs_never_crash_and_always_certify` (120 случайных конфигураций; вручную прогнано 600) |
| При большом `n_invoices` документов могло стать > 200 | выход за предложенный размер эпизода | `n_invoices` ограничен 30..80 (худший случай 199 документов на 600 прогонах) | `test_shipped_configs_meet_proposed_sizes` |
| Генератор мог тихо подправить опубликованный курс, если ошибка выходила слишком мелкой | скачок курса = подсказка, где ошибка | курсы больше никогда не правятся; выбирается другой вариант ошибки | сертификат (`declared_discrepancies_are_exactly_those_present`) |
| `list_records` с `limit: null` давал ошибку | лишний потраченный шаг у LLM-агентов | `null` = страница 50 | `list_records_without_limit_uses_full_page` |
| Упавший процесс оценщика вешал агента или давал невнятную ошибку | зависший прогон до таймаута | явная ошибка `evaluator_process_died` | `dead_evaluator_process_is_reported_not_hung` |

## Что ещё может случиться у жюри

| Риск | Что делать |
|---|---|
| На Windows нет `make` | `python -m auditforge.cli verify` и `python -m pytest -q` делают то же самое |
| Старая версия Python | нужна 3.11+; проверено на 3.11, 3.12, 3.13, результат побитово одинаковый |
| Нет `pytest` | `pip install -r requirements.txt`; сама проверка `cli verify` работает только на стандартной библиотеке |
| Закрытый прогон без секрета | обязательно задать `AUDITFORGE_SECRET` в окружении оценщика, иначе эталон восстановим перебором seed |
| Медленное железо и лимит 60 с | шаг среды занимает миллисекунды, эпизод эталонного решателя около 0,06 с |
| Жюри меняет порядок строк и ID | 20 парных проверок и фаззер уже это делают; ответы oracle не меняются |
| Агент шлёт мусор вместо действий | любые некорректные действия дают ограниченную ошибку и тратят шаг, среда не падает (`malformed_actions_never_crash`) |
| Стратегия «всегда молчать» | диагностическая политика `zero_agent`: +1 на чистых, −1 на остальных; при доле чистых < 50% молчание проигрывает |

## Известные ограничения (не исправлены сознательно)

- Часовые пояса — фиксированные смещения, без DST.
- Изоляция — отдельный процесс, а не песочница; для закрытого прогона нужен отдельный контейнер или пользователь.
- Округление конвертации — общая функция генератора и проверок, единая точка отказа.
